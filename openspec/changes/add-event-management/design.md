# Design

## Context

The bot currently models a per-user PayNow reference (`users` table) and a per-payment description. The `/start` flow is `/init`-gated, then: description → amount → QR. The bot has not been deployed to production D1 yet (task 1.3 is blocked on Cloudflare auth), so schema changes are non-migratory from a running state — we are designing the *first* production schema, not evolving one.

## Goals / Non-Goals

**Goals:**
- One chat can hold many events; each event has one payee and many payments
- `/init` creates an event (name + payee); `/start` picks an event then amount; `/end_event` closes it
- Event name is the SGQR tag 62.01 description for every payment in the event
- `/payments` lists events first, then drills into per-event payments

**Non-Goals:**
- Renaming events after creation (no edit flow)
- Per-payment description override (event name is the fixed description)
- Payee change after event creation (event payee is immutable at create time; new event needed for new payee)
- `users` table deprecation in this change — kept for `/payments` per-user listing; deprecated in a follow-up once events fully replace the per-user model

## Decisions

### D1. Schema: `events` table + `event_id` FK on `payments`

```sql
CREATE TABLE events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  ref           TEXT    NOT NULL UNIQUE,     -- 10-char base32, same generator as payments
  chat_id       INTEGER NOT NULL,
  topic_id      INTEGER NOT NULL DEFAULT 0,  -- 0 = private chat / no topic
  name          TEXT    NOT NULL,            -- ≤ 50 chars
  payee_type    TEXT    NOT NULL CHECK(payee_type IN ('mobile','uen')),
  payee_value   TEXT    NOT NULL,            -- normalized mobile / UEN
  status        TEXT    NOT NULL CHECK(status IN ('open','closed')) DEFAULT 'open',
  created_at    TEXT    NOT NULL,
  closed_at     TEXT
);

ALTER TABLE payments ADD COLUMN event_id INTEGER NOT NULL REFERENCES events(id);
-- existing description column kept (set to event.name at create time, never rewritten)
```

`event_id` is NOT NULL because the spec requires every payment to belong to an event. Since the bot is pre-deploy, we ship this as the canonical schema. Migration generated by `drizzle-kit generate`; applied when task 1.3 provisions the D1.

### D2. Ref generator reuse

Same 10-char base32 via `crypto.getRandomValues` (`src/db/proxy-validation.ts:generateRef`). Event refs will naturally live in the same collision-safe space as payment refs.

### D3. Event name length + SGQR truncation

Event name max 50 chars (UI input). When embedded into tag 62.01, existing `truncateAnsi(..., 25)` applies — matches the SGQR ANS limit. The truncated name goes into the QR; the full name stays on the event row and the payment-row `description` column.

### D4. Chat + topic isolation

Events keyed by `(chat_id, topic_id)`. Private chats → `topic_id = 0` (Telegram's convention when `message_thread_id` is absent). Bot reads `ctx.chat.id` and `ctx.message?.message_thread_id ?? 0` at `/init` time and stamps both onto the event row. `/start` and `/end_event` filter events by `(chat_id, topic_id)`.

### D5. Conversation DO flow states

```
init-name     → step 1: event name
init-payee    → step 2: mobile / UEN
init-confirm  → step 3: echo + "confirm" / "cancel"

start-pick-event → step 1: inline list of open events (auto-advance if exactly 1)
start-amount     → step 2: amount prompt

end-pick-event   → step 1: inline list of open events
end-confirm      → step 2: echo + "confirm" / "cancel"
```

States are orthogonal to existing `payback` and `payments` states — no collisions. `init` state from the old flow is replaced; any stale `init` state in a running DO resolves naturally via the 10-min alarm.

### D6. /payments event-first flow

Top-level: list events in the chat (open + recently-closed, sorted by `created_at DESC`), each showing payment count + collected + pending. Inline buttons per event: "View" → drill into payment list for that event. Payment list reuses existing buttons (View detail, Mark as Received, Payback).

### D7. Close event CAS

`closeEvent(ref, timestamp)` runs a guarded update: `UPDATE events SET status='closed', closed_at=? WHERE ref=? AND status='open'`. Rows affected === 0 means already closed (idempotent) — second button tap shows "already closed".

### D8. Event close does not alter payments

Closing is event-only. `pending` payments in a closed event stay `pending`. Paybacks against received payments in closed events still work — the bounded-payback logic (`sumPaybacks` vs `payments.amount_cents`) is per-payment and event-agnostic.

## Risks / Trade-offs

**[Risk] Stale inline buttons for just-closed events** → Mitigation: the button handler re-reads the event by ref and rejects if `status !== 'open'`. Telegram can't retract in-flight button rows.

**[Risk] Many open events in one chat (10+)** → Mitigation: show up to 10, sorted by `created_at DESC`. If more, add a "… and N more" footer. Paginate only if real usage demands (defer to follow-up).

**[Risk] Pre-existing payments in the wild lack `event_id`** → Mitigation: no production DB exists yet (task 1.3 blocked). Schema ships with `event_id NOT NULL`. If a migration scenario emerges (e.g., user deployed before this change), we'd add a one-time data migration setting `event_id` to the latest open event per user — but that's out of scope here.

**[Trade-off] `description` column duplicated onto payments row** → Keeps the payment row self-contained for reporting and export. Trade-off is storage vs. query simplicity; acceptable at projected volume (events × payments per event ≈ small).

## Migration Plan

1. Schema: `drizzle-kit generate` emits a new migration file adding the `events` table and the `event_id` column on `payments`.
2. Test: Workers-pool tests seed events + payments with `event_id`; Node-pool tests unaffected.
3. Deploy (task 1.3): `wrangler d1 migrations apply paynow-db --remote` applies both the initial schema migration and this one. No running DB exists yet, so no live-data migration.
4. Rollback: not applicable pre-deploy. If needed post-deploy, revert the migration (Drizzle supports `down` via `drizzle-kit drop`) and redeploy the old code path.

## Open Questions

- **`users` table deprecation timing** — once events cover the per-user payee case, `users` becomes redundant. Deprecate in a follow-up after this change is proven in production.
- **Edit event (rename / change payee)** — intentionally omitted. Users who need to change the payee create a new event. Revisit if real usage demands it.
